No more code reviews. Fuzz instead.

Agents and colleagues write apps faster than you can read them. appfuzz runs each one thousands of times before it ships and tells you what would break: a crash on an empty list, user text unescaped in the page, one query per row, a call to a server nobody approved. Pass or fail, in CI.

Install on Linux or macOS

$ curl -fsSL https://appfuzz.dev/install.sh | sh

The script checks the download's SHA-256. Or with Homebrew: brew install stephanschmidt/appfuzz/appfuzz

Try it on a demo app right away: appfuzz --human https://appfuzz.dev/demo/chatty.wasm (five demos). On your own app: appfuzz review next to its .wasm.

A sandbox per request is how production runs already.

WebAssembly isn't a lab experiment. The big edge and serverless platforms give every request, or every function, a sandbox of its own: it starts fast, can touch only what it's given, and is gone afterwards. Your platform can do the same with your apps.

Fastly Compute

WebAssembly, one instance per request

Every request gets a fresh WebAssembly instance, started in microseconds and thrown away afterwards. It runs on Wasmtime, the same runtime appfuzz runs your app in.

Cloudflare Workers

V8 isolates, JavaScript and WebAssembly

Thousands of customers' code side by side in one process, each in an isolate that sees only its own memory. WebAssembly modules run in the same isolates.

Bunny Edge Scripting

Deno on V8, WebAssembly built in

Each script gets an isolated runtime with only the standard Web APIs. WebAssembly support is built in, so any app compiled to Wasm runs at the edge.

AWS Lambda

Firecracker microVMs

Each function runs in its own microVM that handles one request at a time. Not WebAssembly, but the same idea: isolation per tenant and request is the default, not a luxury.

Why this matters with agents: an app an agent wrote, or one a prompt injection talked into misbehaving, can only call what its Wasm sandbox grants. No file system, no network, no other app's memory unless you gave it, and nothing left in memory for the next request. appfuzz checks what the app does with the grants it has.

Two synthetic components · three search seeds · one worker

Get past the first condition.

Different inputs can make the same host calls and return the same page, right up to the one that crashes. Turn on --internal-feedback and appfuzz looks inside the compiled Wasm to guide the search.

It records control-flow hits and integer comparison operands in a temporary instrumented copy. Inputs that reach new paths or get closer to satisfying comparisons stay in the corpus. Observed values guide changes to request numbers and string bytes.

No source changes or special fuzzing build. Every candidate runs on the original component for bug reports and resource measurements.

One fixture hides a crash behind computed numeric comparisons, another behind byte comparisons with no embedded keyword. Internal feedback found both across all three seeds, under a one second budget and a 1,000-evaluation budget, and every crash was confirmed on the original Wasm. A controlled mechanism test, not a general detection rate. Reproduce the experiment.

compare the search
$ appfuzz -j 1 fuzz --fresh --time 10s
$ appfuzz -j 1 fuzz --fresh --time 10s \
    --internal-feedback

Internal feedback is off by default: it runs fewer requests a second, and on the 77 test apps it found nothing extra. Turn it on for parsers, checksums and computed checks. Reports show instrumented modules, skipped code and fallback reasons. Findings replay on the original Wasm.

Find the bug behind a valid request.

A parser that accepts the input. Two sizes that multiply. A backend that fails halfway through. appfuzz searches the conditions that get your app into trouble.

Get past the parser.

JSON and CSV, still valid

Change nested values and list sizes inside JSON, or change CSV cells and rows while keeping the header and column count. The payload stays valid, so the search reaches the code after the parser.

A valid order with quantity zero can reach a division that random text never gets near. Seed a valid payload in your request or host plan; appfuzz mutates both.

appfuzz review

Find the costly combination.

several input sizes, together

Sixteen customers for one day may be fine. One customer over sixteen days may be fine. Both together can mean 256 host calls. appfuzz grows request fields and host lists, and keeps every input that sets a new high in fuel, memory, host cost, latency or output size, so sizes that only hurt together still surface.

Each high is measured against your platform's budgets: over the limit is a fail.

appfuzz review

Fail the seventh call.

one failure, then an outage

The first save works. A later one fails. appfuzz walks reached calls and tries both a single failure and a continuing outage, including retries the successful request never made.

Find later-call crashes, swallowed errors, retry storms and partial writes. Run the sweep automatically in review, or target one successful run with probe faults.

appfuzz probe faults last

All three run automatically in fuzz and review. Findings use the original Wasm, with confirmation, shrinking and replay. Platform rules and value constraints stay authoritative; overridden fault injections are reported as blocked.

Search is bounded by its budget. Structured mutation needs a valid starting payload; a short campaign may not test every fault position. Read the details.

Components, modules and plugins.

However your platform runs WebAssembly, your apps get the same review: the same search, the same checks, the same budgets, the same report.

ComponentsCore modulesExtism plugins
The standard for new apps, in Rust, Go, Python, JavaScript or C#. Each component describes itself in WIT, so you point appfuzz at the file and start. HTTP handlers on wasi:http (Spin, wasmCloud, wasmtime serve) run as they are. Plain WASI modules on a witx platform such as Fastly Compute. Fastly works out of the box; your own platform takes one config file. Plugins built with any Extism PDK, in any language. appfuzz plays the host your plugins run in, so you test them without your product.

A plain module only says which functions it calls, not what they take, so appfuzz asks which platform it runs on. Not yet simulated: outbound HTTP from Extism plugins. Setup in the README.

Say what a right answer is.

appfuzz knows a crash when it sees one. It can't know that every item belongs on the page, or that the total must match the line items. Whoever asked for the app knows. Write it down once, in the manifest, and appfuzz spends the whole search trying to break it.

[acceptance.checks.every_item]
origin = "marketing"
let.rows = "select li"
let.items = "host.items#all.result"
assert = "size(rows) == size(items)"

fail acceptance_failed acceptance check every_item failed

why size(rows) == size(items) is false; rows: [], items: [{"id": 7, "name": "pine sage", …}]

The chatty app from the walkthrough drops an item when its lookup fails, and still answers 200. No crash, nothing unescaped, so no other check fires. The search broke the assert on its 13th request and shrank the case to one item.

Checked on every request
Not one test at the end. fuzz and review check each assert against every request they try, so it breaks wherever the search finds the input.
Goes for the edge
An assert that holds at 99 but not at 101 tells the search where to look. appfuzz keeps the inputs that come closest to breaking it and tries the limit and its neighbors.
Flags asserts that test nothing
appfuzz changes the values an assert reads. If it still holds, the assert only restates the code, and you get a warning instead of a false sense of safety.

Let your agent do the digging.

Marketing builds a dashboard, Sales a calculator. An agent writes each in an afternoon, and nobody has time to read them. The review on deploy gives you a verdict. When a finding needs a closer look, hand it to your agent: it can find out why a run is bad, where an argument came from, whether a suspicion holds, all without the source.

JSON with a next step
Your agent doesn't guess what to run. Every output is one JSON document that lists the commands worth running next, ids filled in.
App text stays data
An app can't talk your agent into a pass. Text the app wrote comes back marked untrusted.
Suspicions become tests
Think "this can't go over 100"? check searches for a counterexample and hands you the one it finds.
Same input, same result
A finding from CI reproduces on your laptop. Time and the backend are simulated, so every run replays exactly.

What the sandbox blocks, nobody has to review.

Reviewing an app written by marketing usually means reading every line for what it might do: write to ORDERS, flood a server, delete files. Run as WebAssembly in a shell, the app can call only the imports the shell grants. If it can't write ORDERS, nobody has to check that it doesn't. The review shrinks to what is granted, and appfuzz tests that.

Not granted

orders.update, sockets, files, processes. The app can't call them, so there is nothing to review.

Granted

items.get. That is what's left to review, and appfuzz tests every call through it: n+1 queries, crashes, odd values.

Limited

You set budgets for CPU, memory, cost and latency in the manifest. appfuzz tells you before it ships whether the app stays inside them.

Experimental: what if the app is up to something?

The sandbox decides what an app can call, not why. An app written by an agent can use a granted fetch to report every page view to a server of its own, send your API key out in base64, leave a note telling your reviewing agent to look away, or wait for a day no test simulates. appfuzz tells you where granted calls go, what they carry, and which calls never ran.

If you run a platform like AppOS.

AppOS lets marketing ship to production the way apps ship to your phone. Engineering owns the shell. Each app runs in a WebAssembly sandbox and does only what its manifest grants. appfuzz is the automatic app review: every app is checked before deployment; incomplete reviews cannot pass, and nobody waits for a human reviewer.

The AppOS architecture slides

Manifest
Marketing and engineering agree on what an app may call. appfuzz reads the same grants and tells you about any import outside them.
App review
Before deploy, appfuzz fuzzes the app against simulated host functions: crashes, n+1 queries, injections, leaks.
Sandbox
Engineering sets production budgets for I/O, time, CPU and memory. appfuzz tests those limits. Experimental envelopes can additionally constrain behavior observed in an accepted review.
Code review
Marketing writes down what the feature must do, as asserts in the manifest, and every review checks them. Engineering owns the platform contract. appfuzz automates routine implementation review against that contract.

Not another test framework.

appfuzz runs the .wasm you deploy, in any language. It plays the database, APIs and services your app calls: it answers with values that fit your app's types, or with data you describe, and varies them. Empty lists, huge lists, errors, odd text. Then it measures what your app does.

Unit tests, proptest
You write the inputs and the checks. appfuzz brings both: it generates requests and backend answers, and already knows the bad patterns. Your own asserts are optional.
cargo-fuzz, libFuzzer
Find crashes in a fuzzing build of your source. appfuzz runs your release build and also reports slow pages, XSS, leaked data and wasteful calls, not only crashes.
Semgrep, CodeQL
Read the code and match patterns. appfuzz runs it, so every finding comes with the input that causes it and a file to replay it. Use both.
Load tests
Tell you in staging that a page is slow under traffic. appfuzz tells you before it ships that the page makes one query per row, and at which table size it breaks its budget.

What it won't do.

A pass means the search found nothing. That's evidence, not proof.

Prove an app is harmless
It finds the usual tricks: servers of the app's own, data in disguise, notes to the reviewer, code waiting for a trigger. A careful author can hide better. The envelope catches some of that in production.
Know your business rules
It can't tell that create writes or that a field is an email address. Labels in the manifest tell it: SQL, secrets, personal data, writes, who owns a record. Asserts tell it what a right answer is.
Simulate concurrent requests
Configured request sequences share modeled backend state and can expose double submits. They run sequentially; live services and concurrent execution remain outside the model.
Measure every branch
Internal feedback is bounded and instruments directly instantiated core modules. Nested components and GC type groups can remain opaque. Reports identify skipped modules. For interpreted apps, signals describe the interpreter and may be less useful.
