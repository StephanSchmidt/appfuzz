No more code reviews. Fuzz instead.

appfuzz runs your WebAssembly app thousands of times against a simulated backend and finds what a review misses: crashes on empty lists and Unicode, user input in your HTML unescaped, loops that send one database query per row. Pass or fail, in CI.

Install on Linux or macOS

$ curl -fsSL https://appfuzz.dev/install.sh | sh

Then run appfuzz review next to your .wasm.

Tested on components built from

  • Rust cargo, wasm32-wasip2
  • Zig zig, wit-bindgen c
  • TypeScript jco, componentize-js
  • Python componentize-py

Four kinds of bug a quick read lets through.

Each one passes review because the code looks fine. appfuzz doesn't read code. It runs it, with the inputs and backend answers you didn't think of.

Crashes

panics, exceptions, hangs, stack overflows

Empty results, failing queries, Unicode, a leap day, the year 2038. Every crash is shrunk to the smallest input that causes it.

appfuzz probe values

Security

XSS, leaked errors, ungranted imports

Request fields and stored data that reach your HTML unescaped. Internal error text on the page. Imports the platform never granted.

appfuzz review

Database

n+1, nested loops, retry storms

Queries that grow with a list or a request field, the same query twice, a loop that retries a failed write 50 times.

appfuzz amplify

Wrong answers

200 %, order bugs, swallowed errors

Usage above 100 %, a total that changes when rows come back in another order, an error page sent with status 200.

appfuzz probe pairs

Also for ops: CPU and memory that grow faster than the input, slow call chains, busy waiting, one slow dependency that blows the latency budget.

Same bug, four languages, same finding.

appfuzz never reads your source. It runs the compiled component, so it doesn't care what you wrote it in. One n+1 loop, written four times, reviewed with the same limits.

for it in items::all() {
    if let Ok(full) = items::get(it.id) {
        out += &format!("<li>{}</li>", esc(&full.owner));
    }
}

65 KB component. cargo, wasm32-wasip2. About 13,250 runs a second on 24 threads.

for (items) |it| {
    var full: Item = undefined;
    var err: Str = undefined;
    if (!bench_web_items_get(it.id, &full, &err)) continue;
    defer bench_web_items_item_free(&full);
    try out.appendSlice(gpa, "<li>");
    try esc(&out, gpa, slice(full.owner));
    try out.appendSlice(gpa, "</li>");
}

114 KB component. zig, wit-bindgen c, the WASI adapter. About 8,600 runs a second. Also found: libc imports file system access the app never uses.

for (const it of all()) {
  try {
    const full = get(it.id);
    out += `<li>${esc(full.owner)}</li>`;
  } catch {}
}

12 MB component, the JS engine included. About 1,900 runs a second. Also found: a 10 KB name makes esc so slow the request never finishes.

for it in items.all():
    try:
        full = items.get(it.id)
        out += f"<li>{escape(full.owner)}</li>"
    except Err:
        pass

18 MB component, the interpreter included. About 1,940 runs a second. Also found: the runtime imports file system and network access the app never uses.

Fast enough for every push.

Every run is a whole request: a fresh sandbox, simulated host calls, every detector. Time is virtual, so a host that takes 200 ms costs nothing real. Thirty seconds of fuzzing is 400,000 requests to the n+1 app above.

The chatty test app, Rust. appfuzz fuzz --time 30s from a fresh start on an AMD Ryzen 9 3900X, 12 cores, 24 threads.

Built for the agent that wrote the app.

Marketing builds a dashboard, Sales a calculator. An agent writes each in an afternoon, and nobody has time to read them. The same agent can run appfuzz on its own work.

JSON everywhere
Every command prints one JSON document.
Always a next step
Each output lists the commands worth running next, ids filled in.
Suspicions become tests
check turns "this can't go over 100" into a search for a counterexample.
Same input, same result
Time and the backend are simulated. Every run replays exactly.

What the sandbox blocks, nobody has to review.

Reviewing an app written by marketing usually means reading every line for what it might do: write to ORDERS, flood a server, delete files. Run as WebAssembly in a shell, the app can call only the imports the shell grants. If it can't write ORDERS, nobody has to check that it doesn't. The review shrinks to what is granted, and appfuzz tests that.

Not granted

orders.update, sockets, files, processes. The app can't call them, so there is nothing to review.

Granted

items.get. appfuzz fuzzes every call the app makes through it: n+1 queries, crashes, odd values.

Limited

CPU, memory, cost and latency have budgets in the manifest. appfuzz measures the app against them before it ships.

The app review in AppOS.

AppOS lets marketing ship to production the way apps ship to your phone. Engineering owns the shell. Each app runs in a WebAssembly sandbox and does only what its manifest grants. appfuzz is the automatic app review: it checks every app before it runs, pass or fail, with no human bottleneck.

The AppOS architecture slides

Manifest
Marketing and engineering agree on what an app may call. appfuzz reads the same grants and flags any import outside them.
App review
Before deploy, appfuzz fuzzes the app against simulated host functions: crashes, n+1 queries, injections, leaks.
Sandbox
In production every request has a budget for I/O, time, CPU and memory. appfuzz measures the app against the same budgets first.
Code review
Engineering reviews the manifest. appfuzz reviews the code.

What it won't do.

A pass means the search found nothing. That's evidence, not proof.

Catch malicious apps
Not yet. It finds careless code, not hidden backdoors.
Know your business rules
It can't tell that create writes. Labels in the manifest say which text is SQL, a secret or personal data.
Test sequences of requests
Each run is one request. Double submits are out of reach for now.
See inside interpreters
TypeScript and Python apps are measured just as well from outside, but the search is less guided and runs are slower.
